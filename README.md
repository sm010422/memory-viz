# macOS 메모리 실시간 시각화 도구

macOS의 실제 메모리 구조를 브라우저에서 실시간으로 시각화하는 로컬 웹 서버 도구입니다.  
`vm_stat`, `ps aux`, `vmmap` 세 가지 시스템 명령어를 주기적으로 실행해 데이터를 수집하고, 브라우저에서 렌더링합니다.

---

## 실행 방법

```bash
# 기본 실행 (자신의 프로세스만 vmmap 접근 가능)
python3 mem_final.py

# 권장: sudo로 실행 (모든 프로세스의 가상 주소 공간 접근 가능)
sudo python3 mem_final.py
```

브라우저가 자동으로 `http://localhost:8765` 를 열어요.  
종료는 터미널에서 `Ctrl + C`.

---

## 화면 구성

### 상단 — 물리 메모리 전체 현황
| 항목 | 설명 |
|------|------|
| 총 메모리 | `vm_stat` 기준 전체 RAM 크기 |
| 사용 중 | active + wired + compressed 합산 |
| 여유 | free pages 비율 |
| 프로세스 수 | 메모리 0.1% 이상 사용 중인 프로세스 수 |

**물리 메모리 구성 바** — macOS가 RAM을 5가지로 구분해서 관리하는 비율을 보여줍니다.

| 구역 | 색 | 의미 |
|------|----|------|
| wired | 보라 | 커널이 고정 사용, 절대 스왑 불가 |
| active | 초록 | 현재 프로세스가 실제로 사용 중인 페이지 |
| inactive | 어두운 초록 | 최근 미사용, 스왑 대상 1순위 |
| compressed | 노랑 | macOS가 RAM 절약을 위해 압축한 페이지 |
| free | 회색 | 완전히 비어있는 페이지 |

---

### 왼쪽 — 프로세스 목록

`ps aux` 를 2초마다 실행해 메모리 사용률 내림차순으로 정렬합니다.

| 컬럼 | 설명 |
|------|------|
| 이름 | 실행 파일명 (경로 제외) |
| PID | 프로세스 ID |
| MEM% | 전체 물리 메모리 대비 RSS 비율 |
| RSS | Resident Set Size — 실제로 RAM에 올라온 크기 |
| CPU% | CPU 사용률 |

> **Google이 여러 개 보이는 이유**: Chrome은 탭·확장프로그램마다 별도 프로세스를 띄웁니다.  
> 각 행의 PID가 다른 독립 프로세스입니다.

---

### 오른쪽 — 가상 주소 공간 상세 (클릭 시 표시)

프로세스를 클릭하면 `vmmap --wide <PID>` 를 실행해 **실제 가상 주소 공간**을 시각화합니다.

#### 주소 바 뷰

```
높은 주소 (0x7FFFFFFFFFFF)
│
│  ████ Stack          ← 0x16F404000 ~ 0x16FC04000
│
│  (빈 공간)
│
│  ████ MALLOC_SMALL   ← 0x148000000 ~ 0x14C000000
│  ████ MALLOC_LARGE
│
│  ████ __DATA         ← 0x1000BC000 ~ 0x1000C0000
│  ████ __TEXT         ← 0x1000B4000 ~ 0x1000B8000
│
낮은 주소 (0x000000000000)
```

- **세로 축의 주소값은 실제 가상 주소**입니다. 직접 `lldb` 나 디버거로 확인할 수 있는 그 주소와 동일합니다.
- 각 영역에 마우스를 올리면 오른쪽 패널에 정확한 시작/끝 주소, 크기, RSS가 표시됩니다.
- 4초마다 자동 갱신 — heap이 늘어나거나 새 라이브러리가 로드되는 것이 반영됩니다.

#### 테이블 뷰

모든 영역을 주소값과 함께 표로 보여줍니다.

| 컬럼 | 예시 | 설명 |
|------|------|------|
| 시작 주소 | `0x000100000000` | 16진수 가상 주소 |
| 끝 주소 | `0x000100010000` | 16진수 가상 주소 |
| 가상 크기 | `64K` | 주소 공간에서 예약된 크기 |
| RSS | `16K` | 실제 물리 RAM에 올라온 크기 |

---

## 영역 타입 설명

| 타입 | 색 | 설명 |
|------|----|------|
| `__TEXT` | 파랑 | 실행 코드 (읽기전용, 공유 가능) |
| `__DATA` | 주황 | 초기화된 전역/정적 변수 |
| `__DATA_CONST` | 황금 | 읽기전용 상수 데이터 |
| `__LINKEDIT` | 회색 | 심볼 테이블, 링커 메타데이터 |
| `__OBJC_*` | 보라 | Objective-C 클래스/메서드 정보 |
| `MALLOC_LARGE` | 초록 | 힙 — 큰 객체 (>1MB) |
| `MALLOC_SMALL` | 초록 | 힙 — 중간 객체 |
| `MALLOC_TINY` | 초록 | 힙 — 작은 객체 (<1KB) |
| `Stack` | 분홍 | 스택 — 함수 호출, 로컬 변수, ESP/EBP가 여기서 움직임 |
| `dyld` | 주황빨 | 동적 링커 — 실행 시 라이브러리를 로드하는 영역 |
| `mapped file` | 파랑회색 | 파일을 메모리에 직접 매핑한 영역 |
| `VM_ALLOCATE` | 어두운 회색 | 직접 vm_allocate로 할당된 영역 |

## 가상 주소 vs 물리 주소

이 도구가 보여주는 주소는 **가상 주소(Virtual Address)** 입니다.

```
프로세스가 보는 세계          실제 물리 RAM
─────────────────           ─────────────────
0x000100000000 ──────────→  물리 0x2A3F0000   (지금은 여기)
               (다음 순간)  스왑/압축으로 사라짐
               (그 다음)   물리 0x8B200000   (다시 올릴 때 다른 자리)
```

- 프로세스는 항상 같은 가상 주소로 접근하지만, 뒤에서 물리 주소는 OS가 자유롭게 바꿉니다.
- 물리 주소는 macOS가 커널 레벨에서 관리하며 userspace에서 접근할 수 없습니다.
- 공부하는 ESP/EBP, 스택 프레임 등은 모두 가상 주소 기준입니다.

## CPU 사용량 문제와 해결법

`vmmap` 은 프로세스 전체 주소 공간을 스캔하기 때문에 무거운 명령어입니다.

| 원인 | 내용 |
|------|------|
| Chrome, Notion 등 | 수천 개 메모리 영역 → vmmap 출력이 수만 줄 |
| 갱신 주기 | 기본 4초마다 재실행 |

**갱신 주기 늘리기** — `mem_final.py` 파일 맨 아래에서 수정:

```python
# 현재 설정 (4초)
setInterval(tickVm, 4000);

# 무거운 프로세스라면 10초로 늘리기
setInterval(tickVm, 10000);
```

서버 쪽 캐시 만료 시간도 함께 조정:

```python
# 현재 (3.5초)
if now - cache['ts_vm'].get(pid, 0) > 3.5:

# 10초로 변경
if now - cache['ts_vm'].get(pid, 0) > 9.5:
```

**가벼운 프로세스 선택** — Finder, iTerm, Preview 같은 작은 프로세스는 vmmap이 빠릅니다.  
Chrome, Notion 같은 대형 앱은 vmmap 실행에 2~5초가 걸릴 수 있어요.

## 데이터 소스 및 갱신 주기

| 데이터 | 명령어 | 주기 |
|--------|--------|------|
| 물리 메모리 전체 현황 | `vm_stat` | 2초 |
| 프로세스 목록 | `ps aux` | 2초 |
| 가상 주소 공간 | `vmmap --wide <PID>` | 4초 (선택된 프로세스만) |

서버는 결과를 캐시해두기 때문에 브라우저 탭을 여러 개 열어도 명령어가 중복 실행되지 않습니다.
